#+title: Pandoc Backend
#+options: num:nil toc:nil

* Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:

Snapper includes a universal parser backend powered by [[https://pandoc.org][pandoc]].
The point of this path is to apply snapper’s semantic line-break formatting to *everything pandoc can read*, using pandoc’s document model as structure truth.

When enabled with =--use-pandoc=, snapper obtains a pandoc document AST and classifies regions from *block/inline node kinds* (=Para= / =Plain= → prose; =Header= / =CodeBlock= / =Table= → non-prose structure or code). It does not re-run the hand-rolled line parsers under =src/parser/{markdown,org,latex,rst}.rs= on that path.

Two ways to obtain the AST (same AST→region walker either way):

1. *CLI (subprocess)* — =--pandoc-backend cli= (default) runs =pandoc -t json=. Uses the full reader set of the installed pandoc binary (typst, asciidoc, docx, html, epub, and more).
2. *FFI (in-process)* — =--pandoc-backend ffi= loads =libsnapper_pandoc= (Haskell foreign-library, C ABI). No =pandoc= process; readers are those linked into the library (markdown, org, rst, latex, html, typst at minimum).

* Requirements
:PROPERTIES:
:CUSTOM_ID: requirements
:END:

** CLI backend

Pandoc 2.x or 3.x must be installed and on your PATH.
Verify with:

#+begin_src bash
pandoc --version
#+end_src

If you pass =--use-pandoc= (CLI backend) and pandoc is missing or fails, snapper reports an error (no silent all-prose success).

** FFI backend

Build the foreign library (needs GHC + the pandoc Haskell package):

#+begin_src bash
cd native/snapper-pandoc
cabal build snapper_pandoc
# point snapper at the shared object
export SNAPPER_PANDOC_LIB=/path/to/libsnapper_pandoc.so
# and ensure dependent Haskell .so paths are loadable (see ldd)
snapper --use-pandoc --pandoc-backend ffi paper.md
#+end_src

If the library cannot be loaded, =--pandoc-backend ffi= fails explicitly with =pandoc FFI library unavailable= — never treats the whole file as prose.

* Usage
:PROPERTIES:
:CUSTOM_ID: usage
:END:

#+begin_src bash
# Typst via pandoc CLI subprocess (default backend)
snapper --use-pandoc paper.typ

# Explicit CLI backend
snapper --use-pandoc --pandoc-backend cli guide.adoc

# In-process Haskell/C FFI (requires libsnapper_pandoc)
snapper --use-pandoc --pandoc-backend ffi paper.md

# HTML
snapper --use-pandoc article.html

# Any format pandoc supports
snapper --use-pandoc -f rst document.rst
#+end_src

Format auto-detects from the file extension.
Override with =-f= when needed.

* When to use pandoc vs built-in parsers
:PROPERTIES:
:CUSTOM_ID: when-to-use
:END:

The built-in parsers (Org, LaTeX, Markdown, RST) handle their formats well and run faster for the CLI subprocess path.
Use the pandoc backend when:

- Working with typst, asciidoc, docx, html, or other formats without a built-in parser
- You want structure decisions from the pandoc AST rather than format-specific line heuristics
- You want consistent classification across many formats in one project
- Prefer =--pandoc-backend ffi= when an in-process link is available and you want to avoid spawning =pandoc=

The built-in parsers preserve more source-level structure (pragmas, inline tokens).
The pandoc backend strips format-specific markup since it works through the abstract AST.

* Limitations
:PROPERTIES:
:CUSTOM_ID: limitations
:END:

- Pandoc strips comments, so =snapper:off= / =snapper:on= pragmas do not work through the pandoc backend
- Table content is not preserved verbatim (tables are non-prose structure markers on the AST path)
- Some format-specific markup (Org drawers, LaTeX preamble) gets simplified in the AST
- The FFI foreign library is optional and not required for default builds; wasm/editor bundles do not embed GHC/pandoc
